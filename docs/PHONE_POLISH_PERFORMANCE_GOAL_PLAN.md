# Phone Controller Polish and Performance Goal Plan

## Page 1 - Interaction Polish, Visual Cleanliness, and UI State Discipline

This page is about making the phone controller stop feeling like a prototype. The current app mostly works, but the experience still has the messy feeling of state being layered on top of state: a zoom button can look duplicated or visually crowded, sheets can feel like they are just appearing over whatever was already there, and controls can overlap or remain half-active after the user changes mode. The first job is to make the interface obey one clean rule: every visible control has one owner, one active state, one place in the layout, and one reason to be on screen. The rail should be treated as the main command surface, not a pile of separate buttons. The Zoom button should behave like a single toggle with a stable pressed state and stable label. It should not visually duplicate the settings zoom row, and the settings row should read as configuration, not a second primary zoom command. The app should never show two competing zoom affordances in the same visual area unless one is clearly a sheet setting and the other is clearly the rail command.

The implementation should begin with a full UI state audit in `public/index.html`, `public/styles.css`, and `public/app.js`. Every rail button, every sheet, every sheet opener, and every active class needs to be mapped. The audit should identify where a class is added but not removed, where a button can open a sheet without closing another sheet, and where the follow/zoom/lens settings can become inconsistent with one another. The fix should centralize sheet opening into one function that closes other sheets before opening the requested sheet, updates the rail button active state, and keeps the visual hierarchy predictable. The keyboard, display, settings, and zoom controls should follow the same event discipline. If a rail action changes a mode, it should update the button state immediately. If a rail action opens a sheet, it should not leave another sheet open underneath it. If the user taps outside a sheet or changes orientation, sheets should either remain in a deliberately docked position or close cleanly; they should never float in a visually accidental state.

The Zoom control needs special treatment because it is both a mode and a rendering feature. The rail Zoom button should mean "show me the optimized zoom-follow experience now." Pressing it should turn on auto-follow and the cursor lens, set the viewport zoom to a known useful value if the user is at 100 percent, and visually mark the button as active. Pressing it again should return to normal view, hide the lens, reset viewport zoom to 100 percent, and remove the active styling. The settings sheet can still expose exact zoom level, follow mouse, and cursor lens controls, but those should be secondary controls with smaller styling and clear synchronization. If the user turns off the lens in settings, the rail button state must reflect the true combined mode. If the user drags the zoom range back to 100 percent, the lens should not linger as a stale overlay. This means `updatePreferenceUi`, `updateZoomUi`, `setAutoFollowCursor`, `setCursorLensEnabled`, and `setViewportZoom` need a single shared definition of active zoom mode.

The visual cleanup should also remove accidental debug feel. Text such as hidden counters, temporary statuses, or developer-like phrasing should not appear in the normal phone surface. The touchpad should feel like a purposeful control surface: dark, premium, stable, with a restrained gold cursor hint and clear touch feedback. The cursor hint should return to center smoothly on release, but it should not jump around on first touch. The rail should use equal-width buttons, consistent spacing, and no label clipping. On small iPhone widths, labels should remain readable, and if a label cannot fit, the design should use shorter labels rather than squeezing text. The settings sheet should be dense but not ugly: rows should align, toggles should be obvious, and sliders should not collide with labels.

The orientation behavior must be explicitly designed rather than left to media queries alone. Portrait should prioritize a large live display at the top, a comfortable touchpad beneath it, and the command rail below. Landscape should prioritize seeing the remote screen and still keeping a reachable touchpad, without the status strip stealing screen height. If the phone rotates while a sheet is open, the sheet should reflow or close; it should not cover the core controls in a way that traps the user. Safe-area insets need to be respected so Safari bottom bars and dynamic island areas do not cause controls to look crushed.

Testing for this page should include DOM-level assertions and screenshot-level checks. The tests need to click the Zoom button repeatedly and prove there is only one rail Zoom button, only one active zoom mode, and no duplicate or overlapping sheet state. Tests need to open Keyboard, Display, Settings, then Zoom and confirm only the intended sheet or mode is active. Portrait and landscape screenshots should be generated after those interactions. The acceptance standard is that the UI looks intentionally composed at rest and during mode transitions. There should be no stacked buttons, no half-open sheets, no text overflow, no stale zoom lens after zoom is disabled, and no visible debug residue.

Completion goals for Page 1:
- The rail has stable, single-owner button states for Keys, Zoom, Display, Settings, Ctrl, Win, Codex, and Claude.
- Pressing Zoom cannot create duplicate-looking zoom controls, overlapping sheets, or stale active styling.
- Only one sheet is open at a time unless a deliberate docked layout is implemented and tested.
- Zoom, follow, lens, and viewport reset all synchronize through one shared state model.
- Portrait and landscape layouts keep the screen, touchpad, and rail visually clean without overlap.
- Normal users see no debug counters or prototype-only text in the core controller surface.
- Automated tests prove repeated mode switching does not create UI duplication or stale overlays.

## Page 2 - Mouse Smoothness, Input Timing, and Gesture Reliability

This page is about making the mouse feel smooth instead of jittery. Right now the cursor can technically move and click, but the movement still feels uneven. The user experience should be closer to a high-quality trackpad: small movements should be precise, medium movements should be smooth and predictable, and edge-hold movement should glide instead of stepping. The current jitter can come from several places: raw pointer events may arrive at irregular intervals, acceleration may amplify tiny noisy deltas, client-side coalescing may send uneven bursts, acknowledgements may update the visible cursor in a way that fights stream cursor metadata, and the edge-hold joystick loop may send steps that are too coarse. The plan is to treat the touchpad as an input signal that needs filtering before it becomes desktop movement.

The first implementation step is to instrument the motion path without cluttering the UI. Debug state should record recent raw deltas, filtered deltas, send intervals, acknowledgement intervals, and edge-hold vectors. This should live in `window.__remoteControllerDebug` and diagnostics, not visible on the phone surface. The goal is to identify whether jitter is caused by input event noise, send cadence, server acknowledgement timing, or visual cursor rendering. Once measured, the touchpad path should get a smoothing filter. Raw `dx` and `dy` should pass through a low-pass filter or velocity smoother that respects direction changes but suppresses tiny alternating noise. The filter should be reset on pointerdown and pointerup so a new gesture starts cleanly. It should also avoid adding lag: smoothing should be stronger for small jitter and weaker for intentional fast movement.

The acceleration curve should be tuned to feel less bumpy. The current movement model has virtual gain, acceleration, sensitivity, and precision mode all multiplying together. That can create a "speed bump" feeling if a small change in event timing changes the acceleration too sharply. The new curve should use a continuous velocity function with capped acceleration and capped per-frame delta. Slow movement should remain precise, fast movement should still travel quickly, and sudden changes should ramp over a few animation frames rather than snapping. Precision mode should lower gain but should not change the basic feel of the curve. The sensitivity slider should feel useful across its range, not like a switch between too slow and too wild.

Pointer move sending should be synchronized with animation frames and network timing. It is okay to coalesce pointer moves, but coalescing must not cause visible stepping. The client should accumulate filtered movement during a frame and send one stable movement packet per animation frame or a controlled maximum rate. If movement is very small, it can wait briefly until it passes a threshold, but it should not wait so long that the cursor feels dead. If movement is large, it should send quickly, but capped so the server is not flooded. Critical commands such as pointer down, pointer up, click, keyboard, and scroll must flush pending movement before they are sent so gestures land where the user expects.

The edge-hold joystick behavior needs its own smoothing. When the finger reaches the side of the touchpad, the vector should ease into the edge direction and continue at a stable velocity. It should not alternate left/right or up/down because the finger slightly crosses the threshold. The threshold should include hysteresis: entering edge-hold can happen near the edge, but leaving it should require moving farther back inward. The vector should be smoothed over time, and speed should ramp in over perhaps 100-180 ms. When the finger releases, edge-hold stops immediately and the visual touchpad hint returns to center. This keeps the feature useful for long cursor travel without feeling glitchy.

The visual cursor on the phone must not fight the real desktop cursor. The displayed cursor should prefer fresh acknowledgement data for a short window after input, because that reflects what the host accepted. Stream cursor metadata should take over only when it is newer or when no recent acknowledgement exists. This handoff needs to be smooth so the cursor does not jump backward when a video frame arrives with slightly older cursor metadata. The zoom lens should use the same active cursor source as the main display. If the lens centers on one cursor source while the overlay dot uses another, it will feel broken.

Drag interactions need to be reliable and minimalistic. Double-tap drag should hold left down, move smoothly, and release on the next tap or on cancellation. Long press right click should not accidentally trigger while the user is beginning a drag. Single tap left click and double tap right click should remain crisp and should not be delayed more than necessary. Two-finger scroll should cancel single-pointer movement cleanly, and when scrolling ends the touchpad should not leave a pointer stuck down. Page hide, orientation change, WebSocket reconnect, and Stop should all release held input immediately.

Testing for this page should combine unit-like movement tests and browser interaction tests. Tests should feed a noisy sequence of pointer moves into the touchpad and assert that filtered deltas are smoother than raw deltas while total movement remains close enough. Tests should prove fast swipes still accelerate, precision mode still reduces movement, and edge-hold produces monotonic movement in the intended direction. Tests should verify that pointer down/up flush pending movement in order. A live smoke check should confirm that continuous movement does not collapse the stream, spike latency, or generate repeated reconnects. The acceptance standard is not just "input works"; it is that the mouse feels predictable, smooth, and polished.

Completion goals for Page 2:
- Touchpad movement uses a smoothing filter that reduces jitter without adding obvious lag.
- Acceleration is continuous, capped, and tuned for precision, normal travel, and fast swipes.
- Pointer move coalescing sends steady frame-paced movement instead of uneven bursts.
- Edge-hold movement eases in, uses hysteresis, and does not oscillate at the boundary.
- The phone cursor and zoom lens use a consistent freshest-cursor source without jumping backward.
- Drag, click, long-press, two-finger scroll, and cancellation paths release input safely.
- Tests prove noisy movement is smoothed, edge-hold is stable, and command order remains correct.

## Page 3 - Stream Performance, Rendering Stability, Packaging Quality, and Final Acceptance

This page is about turning the app from "working" into something that can be handed to another person without embarrassment. Performance is not only frame rate; it is the whole feeling of the stream and controls staying alive under normal phone behavior. The base stream is now stable after the black-frame fixes, but the final polish pass must protect that stability while improving speed. The capture path, WebSocket packet path, image decode path, canvas draw path, and input path all need to be treated as one pipeline. If any part stalls, the phone should keep the last good frame visible, recover quietly, and avoid visible blinking.

The stream pipeline should keep the current "last good frame" rule as a hard invariant. The main canvas should never clear to black over a valid decoded frame, and the zoom lens should never paint a black box before a draw succeeds. The client should track pending frame decode age, decode failure count, and fallback usage, but those should remain diagnostics only. If an image decode fails, the app should keep the last good frame, try the data URL fallback when useful, and continue. If frames arrive faster than mobile Safari can decode, the queue should collapse to the newest frame without starving the decoder. This is important because the user cares about smooth video, but a phone cannot always decode every JPEG at full rate.

Performance tuning should be practical. The host should keep fast quality by default for local Wi-Fi, but the frame cadence should not fight input. During active input, frame pacing should favor responsiveness, but it should not send so many frames that the phone falls behind. During idle but visible viewing, the stream should remain smooth enough to see app switches and cursor movement. If the phone reports hidden incorrectly, the server should not starve it. The host diagnostics should report selected quality, target fps, connected clients, visible clients, capture time, frame bytes, dropped ticks, and decode recovery counts. These values are for us, not for the main phone UI.

Rendering should be organized as a small set of invariants. `drawFrame` owns the canvas shell. `drawScreenFrame` draws the live frame and overlays. `drawCursorLens` draws only if it can draw from a valid image. `drawRemoteCursor` draws only when the lens does not. No function should partially clear the screen and then fail. Every drawing function should either complete a coherent frame or leave the previous coherent frame in place. Resize events, visual viewport changes, orientation changes, and zoom changes should redraw from the last good decoded image. They should not require a fresh network frame just to avoid blanking.

The UI polish work and performance work need to land with cache discipline. Every phone JavaScript change that affects Safari behavior should bump the shell version in `public/sw.js`, `public/index.html`, and service worker registration. Host tests must be updated to match. The host console should make the current phone URL clear, including the version query, so the user knows the phone is not stuck on stale code. Packaging should include the current v-number, startup scripts, Node dependency instructions, and a simple run path. The package should not include stale test output or old app bundles that confuse the user.

Final acceptance should be hands-on and automated. Automated tests should cover UI state, movement smoothing, edge-hold, zoom/lens drawing, stream keepalive, host URL versioning, keyboard, monitor select, shortcuts, and landscape layout. Browser screenshots should be captured for portrait normal view, portrait zoom view, settings sheet, and landscape view. A live local run should start the host, refresh the PIN, open the host console, and confirm the phone URL is visible. If possible, a quick phone manual script should list the exact things to test: connect, verify no blink at idle, toggle zoom, move mouse, click, drag a tab, use Ctrl, open Codex/Claude shortcuts, rotate phone, and stop control.

The finished project should feel simple from the outside. The user opens the laptop host, sees the LAN URL and PIN, opens the phone URL, pairs, and controls the laptop. The phone surface should be clean: screen, touchpad, rail, sheets only when needed. The mouse should feel smooth. Zoom should feel deliberate and not glitchy. The stream should keep updating without black flashes. If something goes wrong, the app should recover quietly or show a clear, short status. No one should need to understand the internal capture loop to use it.

Completion goals for Page 3:
- The main stream and zoom lens both preserve the last good image during decode or draw failures.
- Frame pacing stays responsive during input and steady while idle-visible on mobile Safari.
- Rendering functions never leave half-cleared canvases or black overlays after a failed draw.
- Versioning is bumped for every phone client behavior change and host URL tests enforce it.
- Packaging remains clean, current, and easy for another person to launch on local Wi-Fi.
- Automated tests and screenshots cover normal, zoom, sheet, touchpad, and landscape states.
- Final acceptance confirms no idle blink, no zoom-box blink, smooth mouse movement, clean UI state, working clicks, working drag, working shortcuts, and stable reconnect behavior.
